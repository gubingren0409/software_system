# 仍存在的证据边界

1. **合规 vs 官方发表。** `.007` 的本地 SPEC 报告明确 `Run is compliant`，但未见向 SPEC 提交或被其独立发表的记录。课程分析应称“本地完整、报告合规的 Base 运行”，不是“SPEC 官方认证成绩”。
2. **报告器前后 raw 的双哈希缺失。** 当前 `.007.raw` 与历史哈希记录相符，官方单独 reporter 仅处理既有 raw；然而当时并未在 reporter 之前另存一份原始哈希快照。勿扩大为不可证的绝对声明。
3. **失败日志的退出码不可靠。** OOM 运行的 `EXIT_STATUS=0` 与 `NOT VALID` 同时存在。所有自动判定须以完整性/有效标志为准，而非只看进程退出码。
4. **时间戳。** `install.log` 的 OOM 终点错误；WSL 曾在更早的失败运行中跳钟。正式包装器有同步检查逻辑，但该次检查输出没有独立保存。副本文件的创建时间也受到复制影响。正式结果内部时长和顺序有证据支持；跨来源绝对时间需留意这些限制。
5. **历史配置路径。** 原脚本固化 `/mnt/e/software_system/A2/homework02`，与当前 Git 检出路径不同。不能未经修订就宣称“从这个检出目录可直接一键重跑”，也不宜为此重跑或覆盖 `.007`。
6. **硬件与系统指标。** CPU 缓存来自 WSL `lscpu` 虚拟化视图；Windows WMI 的 1984/2401 MHz 是 22:35 的快照，非正式运行中的时钟/热状态。历史三次 compress 没有温度、功耗、频率、GC、背景负载序列，因此无法唯一归因其连续下降。
7. **跨机比较非受控实验。** 官方 1.01/Java 7 结果仅有三条，均为多路 Xeon 服务器，且 JVM 发行构建、内存、线程、OS 与本机均不同；主参考 Huawei 的 OS 软件字段部分保留占位符。比较只说明观察差异。
8. **单项与诊断成绩。** 原 `.008`–`.010` 的 compress 重复虽有效却不合规为完整 Base；新 `.015`/`.016` profiling 也只提供不同 workload 的整进程资源旁证，不能填补 `.007` 的正式迭代硬件计数器空缺。WSL2 中 `perf` 的虚拟化事件映射、整进程范围与工具干扰限制其解释力；`context-switches:u=0` 与 `/usr/bin/time -v` 的非零值矛盾，已不用于结论。04:50 的[遥测采样](../logs/diagnostics/telemetry_feasibility.log)不是旧运行的历史负载，温度/频率接口不可用；当前 WSL kernel `6.18.40.1` 与正式记录 `6.18.33.2` 不同。
9. **工作集和瓶颈。** SciMark small/large 的设计针对不同数据规模，但其 operation 工作量不等。`709.00/100.11` 不能推算“内存慢 7.08 倍”；无 cache-miss、带宽和 CPI 的正式对照测量可证明具体瓶颈。

报告应把“直接测到”、“官方设计描述”和“待验证机制”分别标注；不因单次或跨系统相关性写出单一因果结论。
