# Java 7 GC 事件：采集口径与解释边界

本选做实验在每次测量 JVM 上固定开启 `-XX:+PrintGCDetails -XX:+PrintGCTimeStamps -Xloggc:<ext4 文件>`。这些选项在 OpenJDK 7u75 RI 上实际接受；每轮独立 GC 日志见[`logs/jvm_parameter/gc/`](../../logs/jvm_parameter/gc/)。`-Xmx` 是四档唯一变化的**研究因子**；GC 记录选项在四档相同。Oracle 的 [Java 7 GC ergonomics 文档](https://docs.oracle.com/javase/7/docs/technotes/guides/vm/gc-ergonomics.html)说明 Parallel GC 的自适应分代大小同时受暂停、吞吐与占用目标影响，因此仅凭 `-Xmx` 的标称值不能预言 GC 次数会单调变化。

## 可复算的解析定义

[`build_optional_data.py`](../../scripts/jvm_parameter/build_optional_data.py)按 Java 7 日志的时间戳行识别一次 `GC` 或 `Full GC`；该行中取**总事件**的最后一个 `, … secs]` 时长，不重复累加嵌套的年轻代/老年代阶段，也不把 `[Times: user=… sys=… real=…]` 的 CPU/四舍五入时间再加一次。每个事件的序号、JVM 启动后秒数、类型、暂停秒数、总堆收集前后用量/当时容量与原始行号写入[`gc_events.csv`](gc_events.csv)；逐轮年轻代、Full GC 次数、暂停总和及**GC 事件中观测到的最大总堆容量**写入[`heap_parameter_results.csv`](heap_parameter_results.csv)。后者只是 GC 日志采样到的 committed capacity，不等于 `-Xmx`、真实峰值 RSS 或测量窗口峰值。原始日志始终优先于衍生 CSV，`--check` 会从原始文件重新计算并比对。

这里的 GC 范围是**整个 Java 7 测量进程**，含套件校验、`check`、120 秒 warmup、240 秒正式测量及内置报告尝试；单独用 Java 8 运行的 reporter 不在此 GC 日志内。因此总暂停秒数不是“240 秒测量窗口的 GC 时间”，不能直接除以 240 秒当作该窗口的 GC 开销比例。日志只记录收集事件及其暂停；它不是对象分配率、live-set 大小、CPU 频率、cache miss、JIT 时间或 OS 调度的直接测量。

统计图只用**有效且 GC 日志可解析**的独立进程计算各配置均值/样本标准差；无效尝试的 GC 事件仍保留在逐轮 CSV 和日志中，但中途结束的进程不能与完整 360 秒 workload 当作等长样本相加。即使吞吐与 GC 时间同步变化，也只能说“与某机制一致”，不能在没有阶段对齐和额外遥测时给出单因果结论。

## 有效完整运行的聚合观察

下表均为每组三次有效完整 Java 进程的均值；`—` 表示该组 0/3 有效，不能计算等长样本均值。

| workload | 配置 | GC 事件均值 | GC 暂停均值（s） | 分数均值（ops/min） |
|---|---|---:|---:|---:|
| compress | 默认 / 512 / 1024 / 2560 MiB | 184.333 / 263.667 / 220.667 / 184.000 | 1.147 / 1.620 / 1.307 / 1.105 | 517.567 / 508.677 / 516.047 / 486.177 |
| derby | 默认 / 512 / 1024 / 2560 MiB | 3394.667 / — / 2887.000 / 2570.000 | 22.351 / — / 260.711 / 17.582 | 717.743 / — / 225.753 / 738.560 |
| sunflow | 默认 / 512 / 1024 / 2560 MiB | 2437.000 / 8128.667 / 4385.667 / 1764.000 | 23.886 / 49.434 / 33.162 / 19.156 | 312.263 / 283.807 / 304.783 / 304.820 |
| scimark.fft.large | 默认 / 512 / 1024 / 2560 MiB | 52.333 / — / — / 69.667 | 4.998 / — / — / 4.409 | 112.123 / — / — / 113.783 |

**观察。** compress 的暂停始终很小，最少暂停的 2560 MiB 反而得分最低，说明 GC 指标不能单独解释吞吐。derby 的 1024 MiB 是最明显的“能完成但频繁 Full GC”区域：暂停均值约为默认的 11.7 倍，同时吞吐低 68.547%。sunflow 随 512→1024→2560 MiB 增大而 GC 事件与暂停下降，但默认分数仍最高。FFT large 在可完成的默认/2560 MiB 两组中 GC 暂停相近，分数差也只有 1.481%。

**机制解释。** Java 7 RI 在本机选择 Parallel GC/自适应分代。较小最大堆会限制年轻代/老年代可扩展空间；当 workload 的 live set 或并行分配接近容量时，会更早触发年轻代或 Full GC。derby 1024 MiB 和 sunflow 512 MiB 的“更多/更长回收与较低吞吐”符合该机制。超过容量压力区后，减少 GC 不保证继续提高分数，因为应用计算、内存带宽/缓存、同步、JIT、OS 调度与宿主频率仍会影响吞吐。

## 失败运行也是 GC 证据

derby 512 MiB 的三次失败分别记录 13,167 / 12,666 / 12,191 次 GC，其中 Full GC 为 13,111 / 12,616 / 12,133 次；进程总 GC 暂停为 842.018 / 810.015 / 789.865 秒，且 raw/控制台含 OOM。首轮人工按同一 900 秒阈值终止，后二轮由 watchdog 终止；这些不完整进程的持续时间为 956/921/901 秒，故不与有效进程求平均。

FFT large 的 512 MiB 三次均在 63–64 秒内 OOM，每次 121 个 GC、60 个 Full GC；1024 MiB 三次在 69–71 秒内 OOM，记录 68–75 个 GC、33–36 个 Full GC。它们的暂停总和只有约 1.2–1.6 秒，并不表示内存充足：日志显示的是快速到达无法满足分配的容量失败，且套件没有进入正式测量。

这两类失败说明 `java` 退出码不能独立作为有效性判据：这些 SciMark OOM 轮的外层退出码仍为 0。解析器因此联合检查 raw/TXT、正式分数、`NOT VALID`/OOM 与日志完整性。

## 因果与测量限制

GC 图中的暂停为日志事件持续时间求和，未区分 warmup 与 measurement，也不含并发阶段、分配等待、CPU 消耗或 OOM 之外的所有停顿；不能直接除以 240 秒。`-Xmx` 还会通过 ergonomics 间接改变分代尺寸与扩展策略，实验没有固定 `-Xms`，这是刻意保持“只改 `-Xmx`”的设计而非遗漏。没有 JFR（Java 7 RI 环境）、heap dump、对象年龄直方图、硬件计数器、频率/温度或同步宿主负载序列，因此结论限于“在本机本 JDK/线程设置下的关联”。
