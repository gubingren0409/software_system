## 2. 原件与正式工作副本

老师原件 `code/original/matrix_multiplication.c` 未修改，复核 SHA-256 为
`188d011109c4470e1f41829216e8677a5c2d8f2b7c8a44215652320dbdf6de15`。

正式工作副本位于 `code/working/`：

- `matrix_multiplication.c` 默认 `MATRIX_N=4096`，诊断构建可用宏覆盖；严格接受
  `--block-size`、`--seed`、`--input`、`--reference`，并要求 `1 <= s <= n`。
- 保留老师 `ih-jh-kh-il-kl-jl` 的核心循环次序、边界判断和 `C += A * B` 语义。
- 输入生成规则为 `splitmix64-interleaved-v1`，默认固定种子 `20261008`；另支持
  `zero` 与 `identity`，规则定义在 `matrix_input.h`。
- 用 `CLOCK_MONOTONIC` 和 `double` 计时；只将核心矩阵乘法放入计时区。读取
  reference、逐元素验证、checksum 和 JSON 输出均在计时区外。
- 每个结果元素、reference 元素、绝对/相对误差、两侧 checksum 与时间都必须为
  有限值。预先固定判据为
  `abs_error <= 1e-12 + 1e-12 * abs(reference)`。
- 标准输出只有一行 `matrix-multiplication-result-v1` JSON。退出码约定为：0 成功，
  64 参数拒绝，65 校验失败，70 内部或 I/O 失败。

`reference_generator.c` 是独立的非分块实现：小尺寸用完整 `long double i-j-k`，
正式尺寸用 `double i-k-j` 生成一次 reference，并用 16 个预先固定坐标的
`long double` 点积复核。零矩阵和单位矩阵还做全矩阵解析检查。reference 构建、
生成与候选计时相互独立。

关键代码定位：参数与主程序见 `code/working/matrix_multiplication.c:128`，单调计时与
老师循环见同文件 `:140`、`:147`，有限性校验见 `:208`、`:266`；独立 reference
入口与样本复核见 `code/working/reference_generator.c:135`、`:197`、`:230`。

## 3. 统一运行接口

- `ConfigSpace` 从 `configs/config_space.json` 载入四个优化级别与五个块大小，并
  生成固定顺序的 20 个配置。
- `TargetAdapter` 从 `configs/target.json` 载入源码、编译器与参数，将尺寸和优化
  级别固化到构建、块大小留作运行参数。构建键包含所有源码/头文件哈希、编译器
  绝对路径与完整版本、完整有序编译命令、尺寸、优化级别及诊断 fault 标志。
- `Evaluator` 负责 reference、资源门禁、超时、`/usr/bin/time -v`、严格 JSON
  解析、正确性门禁与证据落盘。它明确区分 `parameter_rejected`、`crash`、
  `timeout`、`compile_failure`、`validation_failure`、`output_parse_failure`、
  `reference_failure` 和 `resource_rejected`；仅 `success` 有有限性能分数。

接口实现位置为 `autotuner/core.py:81`（ConfigSpace）、`:123`（TargetAdapter）、
`:215`（候选构建）、`:484`（Evaluator）和 `:672`（退出/故障分类）。

构建、reference 和性能结果位于三个独立缓存命名空间。正式测量默认重新运行，
性能缓存仅供显式的中断恢复。每次运行保留命令、stdout、stderr、退出码、核心时间、
进程时间、校验结果、前后资源和来源哈希。大矩阵 reference 及二进制构建在 WSL
本地 `/var/tmp/matrix-autotuner-p1-10245102457/`，Git 只保存 manifest 与哈希。

## 6. 冻结的正式测量与搜索设计

正式测量协议保存在 `configs/measurement_protocol.json`：串行、同一输入、先正确性
门禁、一次预热、五次有效测量、中位数计分；任一次失败则整个配置无效。候选核心
时间与构建、reference、验证、进程墙钟和总调优成本分开记录。由 P1 最大实测进程
墙钟的三倍向上取整，O0/O1/O2/O3 超时分别为 `1271/244/151/243 s`。

`configs/search_protocol.json` 在查看完整 Grid 前冻结：

- Grid：优化级别外层、块大小内层，完整评估 20 个配置，不提前停止。
- 无放回随机：每个种子用 Fisher--Yates 生成 20 配置排列；预算 4、8 是同一条
  12 次轨迹的前缀。
- 随机重启贪心：每次只改变一个参数到任意其他合法值，所以每点恰有 3 个其他
  优化级别邻居和 4 个其他块大小邻居，共 7 个；随机选择未评估起点/重启点，邻居
  以种子打乱，只接受严格改善，平局按规范顺序；无未评估邻居或无改善时重启。
- 初始种子为 `20261008` 至 `20261012`。两种随机算法各种子、各预算只可见自身
  已测数据。最终候选另行独立复测。

完整 20 配置 Grid 的最优有效结果是后续算法质量比较基准。如报告预算 4/8/12 的
Grid 前缀，必须注明其固定的“优化级别外层、块大小内层”顺序，以及此前缀可能造成
顺序偏置。该设计以 `search_protocol.json` schema version 2 记录；R1 发生在任何
正式 Grid 或随机搜索之前。

按四级代表配置进程时间平均，并以每配置 1 次预热 + 5 次测量粗估，完整 Grid 约
`5.3 h`；考虑块大小差异、构建和系统抖动，建议至少预留 6 小时。每种随机算法若
为 5 个种子各执行一条 12 配置轨迹，约为 60 个配置评估、代表性粗估约 15.9 小时；
两种合计约 31.8 小时。4/8 预算直接复用 12 次轨迹前缀，不重复付费。正式实验必须
先满足 4 GiB 宿主/WSL 与后台负载门槛，否则等待并记录而不计分。
